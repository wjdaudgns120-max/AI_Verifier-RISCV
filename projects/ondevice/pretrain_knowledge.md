# [사전학습] YOLO26s 기반 교육장 출입 인원 관리 시스템 (On-Device AI)

이 문서는 평가 에이전트가 프로젝트를 평가하기 전에 학습해야 할 배경지식, 프로젝트 구조, 역할 분담(R&R)을 정리한 것이다.
평가 대상 자료(최종 결과보고서 텍스트, 추론 시스템 소스 코드, 모델 메타데이터)는 이 문서 뒤에 첨부된다.

---

## 1. Overview: 도메인 지식

### 1-1. On-Device AI
- 클라우드 서버 없이 엣지 장치(이 프로젝트에서는 Raspberry Pi 5, ARM Cortex-A76 4코어, GPU/NPU 미사용)에서 직접 추론한다.
- 장점은 서버 독립성, 영상 데이터 외부 전송이 없는 데 따른 보안/프라이버시, 낮은 응답 지연이다. 대신 CPU, 메모리, 발열(쓰로틀링) 제약이 크다.
- 그래서 설계 판단의 핵심은 "정확도 대비 연산량"이며, 정량 목표(FPS, CPU 사용률, 지연)와 그 근거가 필요하다.

### 1-2. 모델 경량화 기법
- 모델 선택: 같은 계열 내 크기(n < s < m)와 task(detect vs seg). seg는 마스크로 가림/경계 판정 정확도가 높지만 후처리 비용이 크다.
- 입력 해상도(imgsz): 연산량은 해상도 제곱에 비례한다. 640→320이면 대략 1/4이지만 작은 객체 검출력이 떨어진다.
- 추론 엔진: PyTorch(.pt) 대신 NCNN 같은 모바일/ARM 최적화 엔진을 쓰면 CPU 추론 속도가 크게 개선된다.
- 정밀도: FP32→FP16으로 모델 크기가 절반이 되고, 정확도 손실은 대개 미미하다.
- 스레드 관리: OpenMP busy-wait 끄기(OMP_WAIT_POLICY=PASSIVE), 프로세스별 스레드 수 제한으로 코어 경합과 불필요한 CPU 점유를 줄인다.

### 1-3. 객체 추적 (Multi-Object Tracking) 과 ByteTrack
- 검출(Detection)은 프레임 단위이고, 추적은 프레임 간 동일 인물에 같은 ID를 부여한다.
- ByteTrack: 높은 신뢰도 박스를 먼저 매칭한 뒤 낮은 신뢰도 박스도 기존 트랙과 2차 매칭한다. 가림(occlusion) 상황에서 ID 단절을 줄이며 연산이 가볍다(Re-ID 특징 불필요).
- 핵심 파라미터: track_high/low_thresh, new_track_thresh, track_buffer(분실 유지 프레임), match_thresh.
- 위험 요소: ID switch, 분실 후 새 ID 생성(이중 카운트), FPS가 낮을 때 프레임 간 이동량이 커져 매칭 실패.

### 1-4. 분산 처리 / 실시간 스트리밍 시스템
- 여러 보드에 역할(캡처, 추론, 후처리)을 나누면 단일 보드의 CPU 병목을 피할 수 있다. 대신 네트워크 지연, 프레임 순서 역전, 노드 장애 처리가 필요해진다.
- 설계 체크포인트: 통신 프로토콜 명세(헤더 구조), 부하 분산 방식(라운드로빈 vs pull 기반), 순서 재정렬과 타임아웃, 재연결, 백프레셔(최신 프레임만 처리), 노드 추가 시 확장성.

### 1-5. 출입 카운팅 알고리즘
- 문 쪽(A)과 실내(B) 구역을 정의하고, 트랙 ID의 "출신 구역 → 현재 구역" 전이로 IN/OUT을 판정한다.
- 어려운 경우: 동시 출입(2명 이상), 경계선 근처 진동(히스테리시스 필요), 가림 후 재등장, 화면 밖으로 사라짐(timeout 기반 OUT), 한 사람의 이중 검출(NMS IOU 튜닝).

## 2. 세부 내용: 이 프로젝트의 구현

### 2-1. 목표 (보고서 기준)
- 정성 목표: 2명 이상 동시 출입 시 누락 없이 카운트, 브라우저로 접속하는 웹페이지 제공.
- 정량 목표: FPS 12 이상. 근거: 사람 이동 속도 N m/s에서 1/N초당 1m 이동하므로, N fps 미만이면 1m 이상의 이동 정보가 소실된다. 달리기 속도 약 12 m/s를 가정했다.

### 2-2. 모델 설정 과정
- YOLO11n vs YOLO26n → YOLO26 계열 선택.
- YOLO26n을 보드 1대에서 쓰면 CPU 과부하가 생겨, 보드를 분업화하고 남는 자원으로 YOLO26s를 선택했다.
- YOLO26s vs YOLO26s-seg → seg 선택(마스크 기반 판정).
- imgsz 640 vs 320 → 320(추론 속도 3배 이상 차이).
- pt vs NCNN → NCNN(크기 감소, 속도 3배 이상).
- FP32 vs FP16 → FP16(크기 약 1/2, 정확도 유지).
- 최종: yolo26s-seg, NCNN, FP16, imgsz 320.

### 2-3. 분산 추론 시스템 (Raspberry Pi 5 × 4대)
- door_master.py (카메라 Pi): 웹캠 640×480 캡처 → JPEG(Q80) → 작업자 2대에 분배. 작업자의 ack를 받은 뒤 다음 최신 프레임을 주는 pull 방식이라 빠른 작업자가 더 많이 처리한다(자동 부하 분산). 실측 CPU 1~2%, RAM 0.5~0.6GB.
- door_worker.py (추론 Pi × 2): NCNN FP16 yolo26s-seg 추론(conf 0.20, IOU 0.60, person class), 윤곽 폴리곤 단순화 후 마스커로 직접 전송, 마스터에 ack. 마스커가 끊겨도 추론은 계속하며 2초마다 재연결한다. 실측 CPU 45~55%, RAM 0.9~1.0GB.
- door_masker.py (판정 Pi): 프레임 번호 기반 재정렬(REORDER_TIMEOUT 0.6s), ByteTrack 추적, A/B 구역 IN/OUT 판정(마스크 무게중심, 가림 비율), 마스크 렌더링, X11 출력, 웹 앱용 파일/제어 포트(6200). 실측(app.py 포함) CPU 4~5%, RAM 0.8~0.9GB.
- app.py (웹, 같은 Pi, 포트 8000): 로그인(SSH 인증), 초기 인원 설정, 실행/모니터링 UI. **평가 대상자 담당이 아니므로 이번 평가 자료에서 소스는 제외했다.**

### 2-4. 판정 알고리즘
- IN: A구역 → B구역 전이. OUT: B구역 → A구역 전이, 또는 2.5초간 track ID 미탐지 후 사라짐.
- LOST_SEC/REAPPEAR_SEC 2.5s(ByteTrack track_buffer 30프레임 ≈ 16fps에서 1.8초보다 길게 설정), 경계 띠(BAND_RATIO), 출신 보완(LINK_GUARD, BIRTH_BAND_RATIO), 마스크 기반 가림 판정.
- 트러블슈팅: 한 명을 두 명으로 카운트하는 문제가 있었다. 원인은 NMS IOU 0.75가 높았던 것으로, 0.6으로 낮춰 해결했다.

### 2-5. 결과 및 한계 (보고서 기준)
- 4대 분업 + 더 큰 모델(yolo26s) → 검출 정확도 향상, CPU 부하 감소, FPS 12 이상 확보.
- 한계(Future work): 장기간 작동 시 카메라 프레임 읽기가 멈추는 현상(door_master 정지)이 있다. 재연결 코드, 로그 수집, 24시간 테스트가 필요하다.

## 3. Role & Responsibility (R&R)

| 팀원 | 역할 |
|---|---|
| 이기광 | 추론 알고리즘 구축 및 실행 파일(.py) 제작 |
| 김서연 | 서비스 웹페이지 프론트엔드 제작 |
| 박율 | 서비스 웹페이지 백엔드 제작 |
| **정명훈 (평가 대상자)** | **추론 알고리즘 구축 및 실행 파일(.py) 제작**: door_master / door_worker / door_masker 분산 추론 파이프라인, 모델 경량화 설정, 추적·IN/OUT 판정 |

- 평가 대상자의 책임 범위: 모델 선택/경량화 결정, 4-보드 분산 추론 구조 및 통신 설계, ByteTrack 기반 추적과 출입 판정 로직, 실행 파일의 안정성.
- 목표: Raspberry Pi 환경에서 FPS 12 이상, 동시 출입 누락 없는 카운팅.
- 평가 관점: 이 프로젝트는 **설계(Design) 관점**으로 평가한다. 아키텍처와 설계 결정이 요구사항(정확도, FPS, 자원 제약)을 근거 있게 충족하는지를 본다.
